## How To Use This Ledger

1. Copy this ledger into the restricted run workbook. Record the actual deployed SHA, environment, scope and actor/tenant fixture aliases.
2. For each feature, execute the linked stable UAT cases and attach the per-step evidence. Test source presence is not evidence that its tests passed.
3. For each endpoint, run UAT-SEC01 with its applicable positive actor, all standard role outcomes, unauthorized/expired/deactivated context, and A/B ID variants. Record the exact expected status from its source/test before sending the request.
4. Add columns for applicability/reason, actual permission response, expected/observed HTTP status, before/after state, audit/job/object/provider evidence, result, defect, tester/date and notes. Use the same method/path as the stable endpoint key.
5. Resolve route placeholders only with returned synthetic fixture IDs. Do not record invitation tokens, bearer credentials, signed links, or secrets. A public route may still enforce a single-use token or rate/input policy.
6. Reconcile this source inventory with the deployed runtime/OpenAPI inventory before sign-off. The count includes conditional routes; absent development-only routes are expected outside Development and require an explicit disposition. Static extraction does not prove route enablement, coverage quality, or authorization correctness.

The inventory contains **429 literal method/path registrations** in Program and the four endpoint modules, plus **24 expanded classification registrations** (six content families × list/detail/history/review), for **453 distinct source route keys**. A permission shown below is endpoint metadata; group identity, active membership, subscription, data-handling notice, service eligibility and relational tenant checks still apply. `ANY(...)` means RequireAnyPermission; semicolon-separated policies are cumulative. Platform helper names link back to their implementation and are not tenant permissions.

External portal package routes use an authenticated customer/development identity with an explicit membership exemption and service-level invitation/package/strong-authentication checks. That exemption is not anonymous or unrestricted tenant access. The standalone external access decision has a different denial contract from package detail/download.

## Source Inventory Limitations And Maintenance

- Program declarations and classification-loop expansion were checked at the recorded baseline. This is not generated from a running application's endpoint metadata. Reconcile runtime/OpenAPI before release; a schema discrepancy is a defect, not permission to guess a request.
- Parameter binding, identity planes, dynamic service checks, classification/notice gates, request transaction exclusions, provider modes, and background-worker enablement are not fully expressed by a route permission cell.
- Shared security changes require the complete affected route inventory and role/context matrix. A representative endpoint or a passing metadata-contract test does not prove all paths.
- Backend, component and browser tests use different providers and fixtures. Keep mocked, in-memory, PostgreSQL and live-provider results separate.
- Enterprise routes are inventoried because they exist in source. Positive provider/provisioning tests remain conditional on approved synthetic scope; do not send real CUI, activate real keys, or configure a real identity provider.
- New endpoints require a stable UAT mapping and expected evidence. Removed/renamed endpoints require compatibility disposition. Do not silently delete historical UAT IDs or carry prior Pass results to a new SHA.
- Unimplemented or undocumented product ideas (for example a standalone program registry or existing-member role editor) remain gaps until a concrete route/UI/service/test supports them. Related readiness metadata is not a substitute implementation.
