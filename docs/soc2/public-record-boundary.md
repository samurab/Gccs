# Public and Protected SOC 2 Records

This operating rule separates public projections from full governance working
records. It is procedural guidance, not a filesystem lock or access-control claim.
The No-CUI posture and existing file-preservation and publication rules still apply.

## Record locations and authority

- Keep full operational context only in a separately accepted protected working-record package. An existing directory, encryption setting or this guide does not approve new intake or establish a permanent evidence platform.
- Keep only reviewed public-safe projections in this repository. Repository ledger, story and runbook links resolve to public projections. Resolve their operative private counterparts through the operator's accepted manifest, not by copying private originals into Git.
- Distinguish retained originals from live private continuation. Retained originals are frozen by procedure and never edited to make them current. An accepted manifest separately binds each source version to its private continuation location, owner, permitted data classes and version-preservation rules; a preservation directory alone is not an approved working-record location.
- If that binding is unavailable, report private continuation as unavailable and continue eligible independent work. Do not reconstruct it from an older public snapshot.
- Preserve the exact original version and its hash before an approved primary-copy replacement. A backup alone never authorizes replacement, disposal or access reduction.
- Historical public snapshots keep their original dates. The public evidence CSV is a disclosed subset, not the entire private register or proof of evidence delivery.

## Subsequent work

1. Reconcile the accepted private continuation version, public projection cutoff and current task authority before editing.
2. Continue only the already-authorized task and accepted data classes. New restricted intake, operations and acceptance decisions retain their separate gates.
3. Preserve version history under the accepted retention/disposition rules. Update the private continuation status when it diverges from the last approved public source binding.
4. Prepare public-safe changes separately, verify claims against their actual source/code/test scope, and obtain exact version-and-destination publication approval.
5. Verify the published commit and align its approved primary copies. Report private progress and pending public projection separately from Git status.

Never use ignore/exclude rules, sparse checkout, hidden paths, private Git commits
on a public release branch, destructive restoration or deletion to conceal pending
records. A clean public checkout does not mean all private work is published.

## Claims and continuing gates

Label implementation, preparation, planned work and unsupported claims separately.
Management self-review is not independent Security, CPA, Legal/Privacy or forensic
assurance. Source tests do not establish deployed operation, measured recovery,
complete retention coverage or certification. This boundary does not authorize
customer/CUI or secret intake, public guides, merges, release tags or deployment.
The separate historical release-evidence population retains its own contract.
