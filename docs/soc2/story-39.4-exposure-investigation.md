### Architecture Assessment And Safe Target Pattern

The current control is intentionally fail-closed, but it is not a scalable steady state:

1. An initial all-zero ref update scans every reachable ancestor, so every new descendant branch or tag inherits the unresolved legacy finding. Because GitHub Actions is post-receive, the ref already exists when the run fails; the check detects rather than prevents creation and does not prove the candidate change introduced the artifact.
2. The implementation performs Git history and tree work per commit and path. The verified initial-push scan ran for about 90 seconds, so repository growth can cause check latency, runner cost and eventual timeout risk.
3. Path suffixes plus short native signatures cannot detect every compressed, encrypted, split, encoded, Git LFS, plain-SQL or unsupported backup representation. A passing result cannot establish that repository history is safe.

Governance is also self-modifiable: no `CODEOWNERS` file exists, required approving reviews are zero, and the policy workflow/checker can currently pass through ordinary pull-request governance. Main protection prevents force pushes and branch deletion, and the active release-tag ruleset prevents tag deletion and non-fast-forward changes. Any approved history/tag remediation therefore requires temporary, exact-target repository-rule authorization, coordination and rollback; it must not be attempted as an ordinary cleanup commit.

The evidence-production workflow also places untracked provider exports and unapproved planning documents under the public-repository working tree without ignore protection. That layout is not safe as a steady-state evidence boundary: an ordinary broad `git add` can stage material that the focused database-artifact checker does not classify. Protected evidence must be moved only through an authorized custody process; any future ignore, staging or publication-control change requires review and must preserve approved sanitized deliverables.

Do not weaken the present gate while the finding is unresolved. After separately authorized containment, establish and approve a clean protected baseline, require full-tree validation of that baseline, retain PR-diff admission checks for new changes, and use baseline-aware handling for descendant initial refs while continuing full-history review for non-descendant or otherwise untrusted refs and governed release tags. Exact post-containment workflow behavior requires security/change approval and focused tests before implementation.

Safe prevention and closure tests must include:

- existing synthetic rejection of an artifact in reachable legacy history for an all-zero initial ref;
- PR-base comparison that passes only when the candidate introduces no prohibited artifact;
- rejection of add-then-delete, rename, modification, nested backup-path, case-variant and signature-disguised artifacts;
- fail-closed behavior for invalid comparison bases without emitting contents;
- post-containment full-tree validation of the exact protected baseline and confirmation that legitimate SQL and sanitized evidence formats remain allowed;
- descendant initial-ref behavior against the approved clean baseline and full-history behavior for non-descendant/untrusted refs; and
- authorized verification of affected branches, tags, release source archives, caches, mirrors and copies that cannot be removed.
