### Critique And Failure Modes

- Treating an email domain, Microsoft-account alias, portal directory label, Global Administrator label, billing role or subscription Owner label as effective Azure root authority can select the wrong identity object or authorization plane. FR-01 reports that the previously used original and corporate-style addresses are aliases of one personal Microsoft account; that report does not make the whole tenant personal. Fresh Entra and Azure reads matched the intended Workforce-tenant Member and active Global Administrator privately, but the exact identifiers remain uncaptured and those roles do not establish Azure root authority.
- Treating Azure global root `/` as the Tenant Root Group conflates different scopes. Global Administrator elevation creates User Access Administrator at `/`; management-group reads target `/providers/Microsoft.Management/managementGroups/<protected-id>`. A denial at the management-group provider scope proves only that principal's read failed there, not that no `/` authorizer exists.
- Treating zero counts returned with access denied as empty role, deny or policy inventories produces a false security and cost conclusion. Likewise, assuming a proposed 30-minute window expires technically can leave root-wide access active because the elevation-created assignment requires explicit removal.
